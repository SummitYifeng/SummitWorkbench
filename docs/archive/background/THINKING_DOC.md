## 1. 一句话愿景

**为我搭建一套"以产品经理身份高效指挥 AI 干活"的个人操作系统**，核心是一个**晨间指挥台**：每天打开它，它告诉我今天要做什么、分别在哪个项目，并能**一键把对应的 AI 工具带着项目上下文拉起来开干**。

它有两条必须分开、但服务于同一目标的主线：

- **知识与记录线**：工作过程、决策、习惯沉淀进 Obsidian，越久越懂我，最终成为 AI 理解我的上下文底座。
- **执行与编排线**：每天知道该干什么，然后把对应的 AI 工具（代码侧 / 飞书办公侧）编排起来跑。

**它不是**：一个连接六个 App 的炫酷同步仪表盘。看板、同步是外壳；内核是"**每个项目的 AI 可读档案**"+"**可复用的任务剧本**"+"**每日编排**"。

## 2. 我的画像与当前痛点

- 身份：**产品经理**。自己写代码已很少（个人 vibe coding 的小项目可忽略），主要工作形态是：拉取开发人员的代码 → 用 AI 读取后做用户体验测试 → 拉分支写新的项目开发需求。
- 工作实体现状：真正的工作活在本地 `~/Documents/Github` 下的 **10+ 个项目文件夹**（Mac 系统），按项目组织。**注意：并非每个项目都与工作相关，也不是每个都要纳入本平台**——初期只会挑选其中几个。
- 知识库现状：Obsidian **裸奔手写、无插件、无工作项目文件**；任务从未在任何系统里被系统化管理（飞书里也只是零散地给自己加日历/任务）。
- 技术能力：能看懂 Python / Node 脚本、会跑命令行、会配 API key。愿意为"自己搭"投入精力，但反对过度工程。
- 核心痛点（一句话）：**每次用 AI 都要手动选一个项目文件夹，再大段口述背景**——重复、低效、且这些背景说完就丢、没有沉淀。
- 这个项目对我的真实意义：我用 AI 一段时间了，能做的事变多了，但**到了一个需要把工作方式再一次重构的节点**，想借这个平台让未来更轻松。**这也是我重新整理工作、并新建 Obsidian 工作知识库的契机。**

## 4. 市场对标结论（精炼版，供 Claude Code 参考）

**总体判断**：这套需求的"连接层"在 2026 年已基本标准化，共同协议是 **MCP**。六个系统里有四个天然说 MCP 或可脚本化。**真正的工作量不在"连接"，而在"编排"和"项目档案"。** 没有任何现成开源项目能一键覆盖全部需求，但组件级都很成熟，缺的只是一层薄薄的编排胶水。

- **飞书（枢纽，支持最好）**：官方开放平台提供 MCP + OpenAPI，覆盖消息、日历、多维表格、云文档、任务（含子任务/任务清单）。可走官方 `lark-openapi-mcp` 或社区 `feishu-mcp`。需在开放平台建**自建应用**、拿 App ID/Secret、配权限、发布。区分**用户身份权限（user_access_token）**与**应用身份权限（tenant_access_token）**——我的场景多为"以我自己身份操作我自己的数据"，偏用户身份权限。
- **Codex（与"项目档案+剧本"设想高度契合）**：
  - `AGENTS.md`：每个项目根目录放一个 = "AI 可读的项目档案"，从此不必每次口述背景。
  - `codex exec`：无交互界面运行，可被脚本 / 定时任务调用，结果输出到 stdout；自动化推荐用 API key 鉴权（`CODEX_API_KEY` 走环境变量）。
  - Skills + MCP：把高频活（拉分支写需求、读代码做体验测试）固化成可复用 Skill。
  - Mac 上有桌面 App 与 CLI（`brew install --cask codex`）。
- **WorkBuddy（松耦合，需注意）**：它是**"接收指令的本地桌面执行器"，不是"能被外部编排的服务"**。集成方式是通过微信 / 企业微信 / 飞书 / QQ / 钉钉**给它发消息派活**，它本地跑完交付文件；内置 MCP + Skills + 文件夹级授权。→ 在本平台里，中枢只能"给它发消息"，不能"直接调用"它。
  - 候选替代：**OpenWorkBuddy**（开源复刻版，本地运行、数据与 Key 不出本机、可切换 DeepSeek/Qwen/GLM/Kimi/Ollama、支持飞书通道与定时任务）。**鉴于 L6（飞书数据尽量本地），OpenWorkBuddy 是更契合的候选，请在 PRD 阶段重点评估。**
- **Obsidian**：本地 markdown 有成熟社区 MCP server，可让 AI 读写库。但当前重点不是"连接"，是"**先定结构**"（见 L7、阶段 0）。
- **可选编排工具**：n8n（可视化自动化、定时触发）或某个 MCP 客户端（Claude Desktop / Cursor / Cherry Studio）当大脑。**是否采用属于开放决策 #1。**

## 5. 推荐架构（三层薄结构）

不做"一个大 App"，而是薄薄三层：

- **记录底座**：Obsidian（全新工作 vault）——所有工作记录、决策、每日笔记
- **连接层**：飞书 MCP + Obsidian MCP（标准协议，近乎零维护）
- **编排层（大脑）**：**⚠️ 开放决策 #1，待 Claude Code 在 PRD 阶段给方案。** 候选：①Claude Code 本身 + MCP 直接编排；②轻量常驻服务 / 脚本；③其他（n8n / MCP 客户端）
- **执行层**：Codex/Claude Code（代码侧，紧耦合、可脚本）+ WorkBuddy 或 OpenWorkBuddy（飞书办公侧，松耦合、发消息驱动）
- **呈现层**：v1 = Obsidian 每日笔记；成熟后再议独立面板

## 6. 分阶段路线图

- **阶段 0 · 打地基（性价比最高，先别碰集成）**
  - 为初期纳入的项目各写一份 `AGENTS.md`（AI 可读项目档案）
  - 建立全新 Obsidian 工作 vault 并定结构（建议 PARA 或"项目 / 领域 / 日记"三层）
  - 完成飞书自建应用的创建与权限配置（我并行做）
  - *做完这一步，即使不接任何集成，"每次选文件夹+口述背景"的核心痛点已解决大半*
- **阶段 1 · 晨间简报**：飞书 MCP → 定时把日历 + 任务拉成一份 daily brief，自动写进 Obsidian 当天笔记
- **阶段 2 · 一键带上下文启动**：为常用项目做启动脚本 / Codex Skill，点一下带着 AGENTS.md 把 AI 拉起来
- **阶段 3 · 剧本库**：把"拉分支写需求""读代码做体验测试"固化成 Codex Skills
- **阶段 4 · WorkBuddy 接入 + 面板（可选）**：飞书办公杂活交给 WorkBuddy/OpenWorkBuddy；到此才评估要不要独立仪表盘

## 9. 风险与替代方案

1. **过度工程（当前最大风险）**：我处在地基阶段，一上来搭 n8n 全家桶 / 独立 App 极可能烂尾。→ 先脚本 + 定时任务跑通，再升级。
2. **WorkBuddy 松耦合**：别指望把它塞进流水线深度编排；要可编排就用 OpenWorkBuddy。
3. **数据 / 密钥安全**：代码与飞书数据会流经这些 agent；Key 走环境变量、按项目最小授权；飞书数据遵守 L6 本地优先。
4. **飞书权限粒度**：注意用户身份权限 vs 应用身份权限的区别，别把能看的数据范围配错。
5. 替代方案：若某集成走不通，飞书侧可退回手动导出 / webhook；编排侧可退回用 MCP 客户端手动驱动。
