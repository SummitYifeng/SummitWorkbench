## 0. 一句话

> 「我相信给了优质的素材才可以有优质的入库，才可以有优质的检索。」
> ⇒ 目标不是「入库一次」，而是**一份能持续照做的留存习惯**。

判断一份素材好不好，**只有一条标准**：

> **它进库以后，能不能被「切块、寻址、溯源」，并且**不被加工污染**？**

- **切块**：库按 `#` / `##` 切块。没有小标题 → 只能整篇引用，答案无法定点。
- **寻址**：引用粒度是 `路径#区块`（例：`logistics/vendors/hotel-xinji#时间线`）。区块标题要**人能读懂**。
- **溯源**：结论要能沿 `分析笔记 → source 原件` 走到底，且原件逐字可核对。
- **不被加工污染**：原件里不能有你的总结；你的总结放分析笔记。两者**永不混写**。

## 1. 一份素材的最小形态（按重要性排序）

1. **一个文件 = 一个单位。**
   不要把三个月、五件不相关的事塞进一个 `XX 全部记录.md` —— 切块后每块都半截。
   ✅ 一次会议 / 一次沟通 / 一次活动 / 一份制度 / 一份计划 = 各自一个文件。
2. **逐字不改。**
   原始措辞本身就是信息（他当时说的是「尽量」还是「必须」，会决定后续判断）。
   加工、提炼、结论**一律放分析笔记**，不要动原件一个字。
3. **头部自包含：日期 / 对象 / 场景 / 参与人。**
   缺了这些，半年后你自己读不懂，检索也认不出「这是谁跟谁」。
   ✅ 建议在文件**最开头**就写清（哪怕只是 4 行）：
   ```
   日期：2026-09-20
   对象：新记酒店（销售 王经理）
   场景：电话沟通（30 分钟）
   参与人：我、王经理
   ```
4. **有 `#` / `##` 小标题。**
   块边界就是 `#` 与 `##`。它决定 `路径#区块` 能不能精确定位到「酒店报价那一节」。
   ✅ 至少按**主题分段**，而不是一大段流水。
5. **「决定了」与「还没定」显式分开。**
   只有原文里**明确写「定了 X」**的才建决策页；「还没定 Y」写进分析笔记的未决区。
   ❌ 不要在事后补编选项 —— 决策页的 `## 选项` 只写原件里**真实出现过**的候选。
6. **文件名稳定可预测**：`<日期>-<对象或主题>-<类型>.md`。
   一旦进库，`source.ref` 就指向它；**改名会让锚点失效**（真要改名走 conventions §5 的重命名流程）。
7. **原件与加工件分开**：原件进 `<线>/sources/`，分析和结论进 `<线>/notes/`（或对象页 / 事件页）。

## 2. 会毁掉检索的形态（反面清单）

| 反面形态 | 后果 |
| --- | --- |
| 只有一个大文件、内部没有小标题 | 块级引用退化成整篇引用，答案无法定点 |
| 只有结论、没有过程 | 无法回答「当时为什么这么定」「还有哪些候选」 |
| 同一份材料换个文件名再放一份 | 幂等键（`ref` + `hash`）能挡住重复入库，但人工判断会混乱 |
| 把「我的总结」当原件入库 | 之后所有引用都指向二手件，逐字校验失去意义 |
| 长表格 / 大段聊天记录不切分 | 单篇贡献几十个块，把别的笔记挤出上下文（历史上踩过：一份 source 贡献 54 块） |
| 文件名叫 `XX_v2_final_最终版.md` | 状态后缀会漂移；版本靠 `status` 与决策互链表达，不靠文件名 |

## 4. 交付给我之前的最小自检（5 问，30 秒）

1. **它是不是「一次事」？** —— 不是就拆开。
2. **文件名是不是 `<日期>-<对象或主题>.md`？** —— 无空格、无 `最终版`。
3. **开头 4 行有没有 日期 / 对象 / 场景 / 参与人？**
4. **有没有 `##` 小标题，且标题本身能读懂？**（例 `## 报价与条件`，而不是 `## 1`）
5. **里面有没有掺进我的总结？** —— 有就挪到分析笔记；原件保持逐字。

全「是」就可以交给我。缺 3 / 4 / 5 是最常见的，也是最贵的三项。

## 5. 我入库时会怎么处理（C-lite 三件套）

```
你的原件
  │ ① 归档为 source 页（逐字、不可变、记 ref + hash）
  ▼
分析笔记 / 对象页 / 事件页（结论按 ## 分节，每个 ## = 一个可被引用的结论）
  │ ② 提炼「明确的决定」→ 单独成篇放 decisions/（只在原件确有决定时）
  │ ③ 更新主题簇页 / 对象页（## 关键结论 / ## 未决问题 / ## 时间线）
  │ ④ 双链写回正文（1–3 条 + 一句关系理由）
  ▼
回填 index/ 与 projects/ 的主页区块，并 git 提交
```

- **幂等键** = `source.ref` + `source.hash`（原件路径 + 内容 sha256 前 16 位）。
  同一份材料重复入库**不会**产生重复笔记；**同 ref 不同 hash 会报冲突退出**（交人工判断，不覆盖）。
- 幂等判定**只在 `source` / `meeting-transcript` 页上做**；分析笔记 / 决策 / 对象页 / 事件页沿用同一键**不算冲突**。
- 入库后机械校验：所有 `[[页#区块]]` 与 `路径#区块` 必须命中真实标题（`kb_verify_links.py`）。
- **逐字校验**：`kb_verify_quotes.py --materials-root <目录>` 会拿原件**逐字比对**库内 `source` 页。
  所以只要你交的是逐字原件，这一关就自动过得去；如果它红了，说明原件被加工过或路径不对。

## 7. 迭代规则（入库不是定死）

种子基线的价值在于**持续迭代**，所以：

1. **新输入 → 追加，不重写。** 同一个对象 / 人 / 主题有了新进展：在**对象页 `## 时间线` 追加一行**，
   而不是新建一篇「补充说明」。
2. **结论被推翻 → 不改旧文。** 新写一篇决策、旧篇 `status: superseded`，两篇互链（conventions §7）。
3. **原件永不改。** 要修正口径，改的是分析笔记 / 对象页，原件留着供追溯。
4. **规范本身也会迭代。** 若你在实际留素材时发现本文件不合理（例如某个 `##` 标题每次都用不上），
   **告诉我**——改规范 + 改模板 + 改库结构三件事一起做，不允许文档和习惯漂移。
5. **粒度可以升级，不能退化。** 例如一个「物料类别」采购变复杂了，可以拆成按供应商的对象页；
   但不要反过来把多个对象合并成一页。

## 8. 各种格式怎么给

| 你手上的东西 | 怎么给 | 说明 |
| --- | --- | --- |
| Markdown / 文本（会议纪要、计划、手册、构想） | **直接放文件**，放进 `~/Desktop/当前材料/<线>/` | 最理想，逐字校验可机械完成 |
| 飞书文档原文 | 复制成 Markdown 存成文件，或给**文档链接 + 导出文件** | 链接单独不足以做逐字校验 |
| 邮件 | 导出 `.eml` / 复制正文成 `.md`，保留发件人与日期 | 邮件里的时间与收件人是关键证据 |
| 截图 / 照片 / PDF / 表格 | 放 `<线>/sources/attachments/`（≤1MB 进 Git；>1MB 只留引用 + 本机路径） | conventions §12；扫描件建议附一份文字转录 |
| 口头结论（没有书面件） | 你自己写一份**当次记录**当原件（写清「据我记忆，非逐字」） | 必须标注性质，避免被当成逐字证据 |

## 10. 已知不足与未验证（诚实标注）

1. **首批入库已完成（2026-09-14，三线各 1 批），规范通过了第一次实战检验。**
   结论：§3 的粒度与 §3.1 的场景表**不需要改**（按对象 / 按人 / 按事件三处都直接适用），
   但暴露了三条**要你配合的采集习惯**：
   - **原件缺 `##` 小标题**（1977 酒店那份是 5 条编号进展）→ 整份原件退化成**单个区块**，
     块级引用只能落到对象页。建议以后这类进展记录也加 2–3 个 `##`（如 `## 场地与合同` / `## 改造进度`）。
   - **一份文件里混着「定稿 + 过程稿」**（6/7 方案里同时有下午场过程稿与 `New Plan 0526`）→
     我按「**结论层只用最终版，过程稿只留原件**」处理。建议过程稿另起一节，并**显式写明哪个是最终版**
     （这次是靠 `New Plan 0526` 自注「已在前面整体 agenda 更新」才判出来的，属于运气好）。
   - **原稿 + 人工纪要同时给**：你已确认将来**只给原稿**。若某次仍给了人工纪要，我会把它留作
     分析笔记底稿再补结论（2026-09-14 就是这么做的），**不另起一篇竞争的分析笔记**。
2. ~~**微信 / 录音路径未验证**~~ —— **已结案（2026-09-14）**：使用者确认这两类**不会出现**（含将来），
   故不是「未验证」而是「不适用」，§8 已删除对应流程。若日后真的出现口头沟通，按 §8 最后一行自写记录并标注非逐字。
3. **对象页的「一页到底能多长」没有实测**：一个合作 3 年的酒店，`## 时间线` 可能有上百行。
   届时可能要按年切分或把过程细节下沉到 `notes/`——**先按一页滚动，别提前优化**。
4. **流程沉淀的二级形态未定**：事件页 `## 可复用流程` → `clusters/<slug>-sop.md` 的提炼时机
   （规范给的是「复用 ≥2 次」），尚无真实案例。
5. **`hr/people/` 与 `index/people.md`**：索引页由脚本按 frontmatter 聚合再生成，**人页是真源**，
   不要手工在索引页补条目。
