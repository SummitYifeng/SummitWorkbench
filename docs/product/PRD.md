## 1. 项目背景与北极星指标

### 1.1 一句话定义

> **把 `HIC_Logistics` 已验证的「零摩擦 inbox + AI 可读项目档案 + 按剧本执行」模式，从 1 个项目推广到 N 个项目，并建立一套既能跨项目调度行动、又能持续吸收会议与工作记录的「外置执行管理层 + 第二大脑」。**

其中「项目档案 + 执行 + 每日调度」是已验证模式的推广；「会议材料进入工作知识库并反哺行动判断」是二次对齐新增的核心能力，其输入来源、处理时机、模型边界、审核与失败策略已在本版完成规格确认。

### 1.2 用户画像（基于 33 个仓库扫描的修正版）

归档的 `THINKING_DOC.md` 中「自己写代码已很少，个人 vibe coding 的小项目可忽略」的自述与事实不符。实际情况：

- **规模**：本机 33 个 git 仓库，其中约 19 个为工作项目（HIC / Hoffman 系列）
- **技术栈广度**：Go、Spring Boot、React、Vue、Tauri/Rust、Swift、Next.js、Flask、XeLaTeX
- **主要工作形态**：**文档生产**（LaTeX 排版、翻译、手册制作）占比高于软件开发。纳入 MVP 的 4 个项目中有 3 个是文档生产
- **角色**：一个人同时是 5–8 条真实产品线的 owner，而非「偶尔用 AI 的产品经理」

**这个修正直接改变需求定义**：用户要的不是「省下每次口述背景的 5 分钟」，而是「**一个人如何不让任意一条产品线静默停摆**」。

### 1.3 失控的真实形态

| 类型 | 说明 | 是否可自动采集 | MVP 处理 |
|---|---|---|---|
| ① 硬约束 | 会议、评审等已占用时段 | ✅ 飞书日历 | 做 |
| ② 对外承诺 | 答应别人、有截止日期的事 | ❌ 需手录 | 做，但**降为兜底** |
| ③ 项目状态 | 停滞 / 未提交改动 / 输入积压 / README 声明的下一步 | ✅ **完全自动** | **MVP 重心** |
| ④ 想法待办 | 零散念头 | ❌ 手录，压力低 | 做（全局 inbox） |
| ⑤ 会议知识 | 语音转文本中的事实、决策、承诺、行动项与项目背景 | ✅ 飞书纪要 API；失败时本地导入 | **M1 核心能力** |

**设计原则：系统的价值不得依赖用户养成新习惯。** ③ 完全由 git 与文件系统提供，即使用户一条都不录入，简报每天仍有实质内容。② 是加分项，不是生命线。

### 1.4 北极星指标

**主指标 · 信号闭合中位时长**

> 从一个「需要行动的信号」首次出现在简报，到它消失（inbox 清空 / dirty 改动被提交 / 功能分支被合并 / 飞书任务被完成）的天数中位数。
>
> **目标：≤ 7 天，连续 4 周达成。**

选它的理由：直接度量「不失控」，且**完全可自动计算**——每日简报生成时把信号快照落进 vault，与历史快照比对即可。基线在晨间简报里程碑（新 M2）上线后第一周建立。

**护栏指标（任一破线即视为设计失败）**

| # | 指标 | 阈值 |
|---|---|---|
| G1 | 简报「事实区」字段错误数 | **= 0**（每周抽查全部 7 份） |
| G2 | 简报中「需要行动」的条目数 | **≤ 5 条/天** |
| G3 | 每日人工维护耗时 | **≤ 3 分钟** |
| G4 | 简报生成成功率 | **≥ 95%**，且失败必须可见（见 NFR-6） |
| G5 | 可读取完整文本的已发现会议有明确处理结果 | **= 100%**：成功归档或带原因进入可见错误状态，静默遗漏为 0 |
| G6 | 未经确认的会议提取项写入执行系统 | **= 0** |
| G7 | `wb ask` 事实性结论的有效来源覆盖率 | **= 100%**；无证据时必须明确无法判断 |

**滞后指标（不作为 MVP 验收标准）**

- 工作 vault 中带合规 frontmatter 的笔记数、覆盖项目数
- **由环 B 收尾自动生成的笔记占比 ≥ 80%** —— 需要人工补写的越少，机制越健康

> **工作会话的「上下文复利」不单独要求用户维护**，它仍是环 B 收尾动作的副产品；但会议语音转写的归档与结构化处理是明确的产品能力。两者共同进入 Obsidian，成为第二大脑的工作记忆。任何要求用户额外重复整理同一份材料的设计一律否决。

## 3. 核心能力规格

### 3.1 知识库侧

#### 3.1.1 支持的文件格式

**仅 Markdown（`.md`）。**

明确**不做** PDF / Word / PPT 解析。理由：本 vault 的写入方是 AI 与用户本人，不是外部文档导入。项目里的 PDF、docx 源材料归各自项目仓库管理（如 `HIC_SWB_LaTEX/raw/`），vault 只存**工作记录与项目状态**，不存原始资料。

#### 3.1.2 切片策略：块级切分（`#` / `##`）

**检索单元 = 文件内的 Markdown 区块**，不再是整篇文件。

实现口径（2026-09 起，与 SummitKnowledge 共用同一份契约，见
[`docs/contracts/WORK-KB-RETRIEVAL-CONTRACT.md`](../contracts/WORK-KB-RETRIEVAL-CONTRACT.md)）：

- 文首 H1 是笔记标题，不产生独立区块；
- 后续 `#` 与 `##` 是块边界；`###` 及更深留在父块内；
- 围栏代码块里的 `#` 不是边界；
- 首个区块前的正文形成文件级块（`heading=""`），文件级引用仍然合法；
- 重复可引用标题**不得**自动改名成「标题 2」，退化为文件级引用并记录诊断。

为什么改：早期「检索单元 = 一个文件」在本量级已不成立——引用需要精确到「哪一页的哪一节」，
整篇文件作为锚点无法定位；且长文里真正相关的那一节常常排在整篇排序之后。

会议逐字稿始终以**完整、不可变的 Markdown** 归档（证据层）；检索可以在其中定位具体区块，
但原件正文永不被改写。

#### 3.1.3 向量数据库选型：SWB 明确不引入

SWB 的检索实现 = **目录路径约定 + frontmatter 字段过滤 + SQLite FTS5/trigram + Python BM25 降级 + 多信号融合**。

- 索引是**纯派生数据**：坏了可自愈重建，坏了也不连累问答（退回纯 Markdown 子串扫描）。
- FTS5 不可用时自动退化为纯 Python BM25，两者共用同一套 3-gram 词表。
- 融合信号包括：路由优先类型、主题通道、导航型区块降权、证据层降权、同源去重、双链扩展等。
- 结果给出 `路径#区块` 级引用与检索轨迹（命中了哪些块、为什么、排除了什么）。

在单人、数百到数千篇的场景下，**本地方案负责召回，语义精排归 SummitKnowledge**。
SWB 不维护 embedding、不建向量库、不做精排。

**重新评估触发阈值**（写死，避免凭感觉决策——满足任一条即重开评估）：

| # | 触发条件 | 现状 |
|---|---|---|
| T1 | vault 笔记数 > 1500 | 未触发 |
| T2 | 连续 2 周、每周 ≥ 3 次出现「跨项目模糊语义查询」（字面检索无法满足） | **已满足（2026-09-14 登记）** |
| T3 | 本地检索 P95 > 2 秒 | 未触发 |

**触发后的既定方案**：高级语义检索由 `SummitKnowledge` 统一承担（多库切换 + 云端精排 +
多步生成问答），**不在 SummitWorkbench 内新建一套语义检索**。理由见 3.1.6。

**`wb ask` 的定位不因 T2 触发而改变**：它是轻量兜底（结构化检索 + 强制引用），
不扩展为语义 RAG；需要语义检索时走 SummitKnowledge。

#### 3.1.4 召回测试阈值 → 简报准确率 + 引用可解析性

本地检索已存在召回环节，但**不设自动的「质量百分比合格线」**——检索质量由人工用
`scripts/kb_measure.py` 对比判断（另见 `scripts/kb_acceptance.py` 的验收问题）。机器可判定的
硬门禁是：

| 测试项 | 方法 | 阈值 |
|---|---|---|
| 事实区字段准确率 | 每周抽 7 份简报，逐字段比对飞书原始响应与 git 实际状态 | **100%**（硬门禁，任一错误即回滚） |
| 提议区有用率 | 人工标注 20 个「下一步提示」样本，标注「有用 / 无用 / 错误」 | **有用 ≥ 60%，错误 ≤ 10%** |
| 上下文完整性 | 环 B 拉起 AI 后，统计需要人工补充背景的会话比例 | **≤ 20%** |
| 引用可解析 | 验收脚本解析每个返回 anchor 到真实文件与区块 | **任一无法解析即失败（非零退出）** |

#### 3.1.6 与 SummitKnowledge 的边界

> **SummitWorkbench 管「调度、写入与轻量工作问答」，SummitKnowledge 管高级语义检索与长期记忆体验。接口是 vault 里的 Markdown，契约见 [`docs/contracts/WORK-KB-RETRIEVAL-CONTRACT.md`](../contracts/WORK-KB-RETRIEVAL-CONTRACT.md)。**

分工（2026-09 起）：

1. **SWB 是写入方**：决定什么内容以什么状态落到哪一页，并保证自动沉淀的 Markdown 可被稳定索引、引用与判权威（可执行校验见契约 §8）。
2. **SK 是检索方**：支持个人库 / 工作库切换、工作库只读、分库检索策略、云端精排与多步生成问答。
3. **`wb ask` 保持轻量兜底**：不扩展为语义 RAG；需要语义检索时用 SummitKnowledge。

早期「MVP 阶段不修改 SummitKnowledge」的约束**随 T2 触发解除**（见 3.1.3）：工作库已积累到
出现字面检索无法满足的语义迁移问题，改造 SK 支持多库现在是既定路线。工作库对 SK **只读**——
所有写入仍只由 SWB 负责。

**SWB 只付的兼容成本**：遵循 MyKnowledge conventions + 统一 frontmatter + 本契约。

#### 3.1.7 全局 inbox 规格（M0 必须先规范化）

**已知缺陷**：`HIC_Logistics/input/inbox.md` 的「待处理条目」区混杂已归档占位行（如「（2026-08-16 四条输入已处理，见 archive/）」），导致**积压数无法被机器可靠读取**——`wc -l` 会把说明文字和归档标记一并计入。

**规格**：

| 项 | 规定 |
|---|---|
| 待处理条目格式 | 必须以 `- [ ] ` 开头，一行一条 |
| 已处理 | 移出「待处理」区到 `input/archive/`，**不留占位行** |
| 积压数定义 | 「待处理条目」区中 `- [ ] ` 开头的行数 |
| 全局 inbox 位置 | `_vault/inbox.md`，格式同上，条目可带 `#项目名` 标签供路由 |

**M0 交付**：按此规格重整 `HIC_Logistics/input/inbox.md`，并更新其 `AGENTS.md` 中的归档流程。

#### 3.1.8 录入分流规则

| 内容类型 | 落点 | 入口 |
|---|---|---|
| 有截止日期 / 涉及他人的承诺 | **飞书任务** | 命令行一句话创建，含 due date |
| 零散想法 / 项目内条目 | **全局 `_vault/inbox.md`** | 命令行追加一行 |
| 会议中确认的有期限或涉及他人的行动项 | **飞书任务** | 集中待确认页批准后批量创建 |
| 会议中确认的明确项目下一步 | **项目主笔记 `## 下一步`** | 集中待确认页批准后写回 |
| 会议中的未成熟项目想法 | **对应项目 inbox** | 集中待确认页批准后路由 |
| 无法确定目标项目的会议条目 | **全局 `_vault/inbox.md`** | 标记 `unresolved`，不得自动猜测项目 |
| 他人行动项（责任记录，v0.4） | **主档案 `## 跟进事项`** | 审批落点「跟进事项」批准后写回（`- [ ] ` 人工勾选闭环，不进本人待办）|
| 知识线程的未成熟想法（v0.4） | **`_vault/inboxes/<线程>.md`** | 审批批准后路由到线程 inbox |

不同类型的内容承担不同责任，强塞进一个箱子会同时损害提醒可靠性与知识结构。全局 inbox 由 AI 定期路由到各项目 inbox、项目主笔记或飞书任务。

#### 3.1.9 会议知识链路（v1.1 新增，规格已确认）

**目标**：会议语音转写不再散落在聊天、下载目录或会议工具中。系统应将其转化为可追溯的会议备份，并让后续 Agent 能从工作 vault 中持续回答：

1. 我参与和推进过什么；
2. 会议形成了哪些事实、决定与承诺；
3. 哪些事项尚未完成，下一步可能是什么；
4. 这些信息分别属于哪个项目。

**已确认原则**：

- Obsidian 工作 vault 同时承载项目工作记忆与会议记忆，是「第二大脑」的数据底座。
- 会议处理不能只产出一篇孤立摘要；其中的决策、行动项和项目关系必须能够反哺晨间简报与环 B 的启动上下文。
- 必须保留可追溯来源，使 Agent 能区分会议原始内容、AI 提取结果与 AI 后续建议。
- 不要求用户对同一份转写再次手工整理；允许的人工操作仅应是轻量确认或纠错。
- 采用**分层自动化**：原始转写与结构化会议笔记可自动进入会议档案；AI 提取出的决策、行动项、项目状态变化和拟创建任务先进入统一的「待确认区」。只有在用户一次确认后，才允许更新项目主笔记、进入晨间行动信号或创建飞书任务。
- 未确认内容不得被简报当作事实，也不得改变项目的「当前状态 / 下一步 / 阻塞」。简报可以显示“有 N 条会议提取结果待确认”，但不能把其内容混入正式行动排序。

**结构化会议笔记模板（L24）**：

```markdown
---
date: 2026-08-30
type: meeting-note
status: pending-review
meeting_id: <飞书 meeting_id 或本地稳定 ID>
note_id: <飞书 note_id；本地导入时留空>
source: feishu-note
projects: [ProjectA, ProjectB]
transcript: "[[对应逐字稿]]"
model: <实际使用的模型 ID>
prompt_version: <meeting-processor prompt 版本>
---

# <会议标题>

## 一分钟摘要
<!-- 结论、重要变化、最需注意事项；一屏内读完 -->

## 会议信息
<!-- 时间、参会人、来源 -->

## 事实与进展
## 已形成决策
## 明确行动项
## 未决问题
## AI 建议
## 关联项目
## 证据索引
<!-- 指向逐字稿中的说话人 + 时间戳或稳定段落锚点 -->
```

模板是上下双层结构：`## 一分钟摘要` 面向用户快速阅读；其余固定区块面向 Agent 稳定提取。会议明确形成的行动项只进入 `## 明确行动项`，模型推断的下一步只进入 `## AI 建议`，两者禁止混写。

**双文件保存（L15）**：

- 每场会议保存一份完整逐字稿 Markdown，作为证据层；应保留说话人、相对时间戳和飞书来源标识，不与 AI 摘要混写。
- 同场会议另存一份结构化会议笔记 Markdown，作为理解与行动层；必须通过稳定链接关联对应逐字稿。
- 两份文件都进入 `_vault/meetings/` 与私有 git remote，也都可被 Agent 检索与引用；MVP 只在 Mac Studio 运行，未来 Mac Air 通过同一 remote 接入。
- 原始录像体积大且已由飞书保管，不复制进 vault；会议笔记保留录像或会议的来源标识以便回看。
- 所有会议的完整逐字稿均允许交给已配置的云端模型做结构化处理；产品不提供敏感会议分类或 `local-only` 分支。
- 云端模型供应商是可替换依赖。会议处理 prompt 与结构化输出 schema 不得包含供应商专属语法；更换模型不得迁移 vault 数据。
- 不引入本地模型、双路推理、隐私分类规则或本机结果合并逻辑。

**集中待确认页（L21）**：

- `_vault/review/meetings.md` 是会议提取结果影响执行系统前的唯一审批入口，按会议分组展示候选决策、行动项、项目状态变化和拟创建任务，并链接到结构化笔记及逐字稿证据位置。
- 每条候选项必须有稳定唯一 ID、类型、目标项目、拟执行动作和来源引用。缺少目标或依据的条目不可进入可勾选状态。
- 用户勾选条目后，显式运行一次批量应用命令；仅编辑、保存或同步该文件绝不触发写回。
- 应用成功的条目移入 `review/archive/` 留存审计记录；部分失败时成功项不得重复执行，失败项保留并显示原因，允许幂等重试。
- `- [ ]` 表示待确认，`- [x]` 表示批准，`~~条目~~ #ignore` 表示拒绝；用户可在批准前原地修改正文、`target_project`、截止日期和拟写入位置。
- 批量应用命令同时处理批准与拒绝：批准项执行最终编辑后的动作，拒绝项不产生任何业务写回；两者均进入审计归档。
- 审计记录必须同时保存 AI 原始提取值与用户最终值。语法无效或目标不存在的条目不得执行，需留在待确认页并显示校验错误。
- M1 阶段由集中待确认页和 `wb status` 始终显示当前待确认条目数；M2 上线后，晨间简报也必须显示该数量。当待确认条目达到 5 条，或其中最老条目超过 3 天时，发出一次 macOS 分级提醒。只在跨越阈值或严重程度升级时再次通知，避免每轮轮询重复轰炸；积压降回阈值以下后自动解除告警状态。

**跨项目关联（L22）**：

- 结构化会议笔记使用 `projects` 数组保存 AI 初步识别的关联项目，不强制指定唯一主项目；在 `status: pending-review` 阶段这些关联仍是候选，用户批准或修改后再更新为最终关联。
- 同一会议内的每条决策、行动项与状态变化必须单独保存 `target_project`，允许分别路由到不同项目。
- AI 无法可靠判断目标项目时标记为 `unresolved`，不得自行创建新项目名，也不得把条目默认塞入最近使用的项目。
- 项目 Agent 启动时只自动加载与该项目关联的结构化会议笔记摘要及已确认事项；完整逐字稿不进入默认上下文，仅在核查来源时按链接读取。
- 每条候选行动必须在待确认页显示拟写入位置。用户可在勾选前修改目标；批量应用时按「有期限/涉及他人 → 飞书任务；明确内部下一步 → 项目主笔记；未成熟想法 → 项目 inbox；项目不明 → 全局 inbox」执行。

**超长会议兜底（L36）**：常规会议（目前通常不超过一个多小时）优先把完整逐字稿单次交给 `meeting_model`，减少分段造成的信息损失。调用前按实际 token 估算而非会议时长判断；只有输入加预留输出接近所配置模型上下文上限时，才按说话人、时间戳和议题边界建立临时处理段，逐段提取后进行第二层合并去重。最终每条事实、决策与行动项仍必须指回原始逐字稿时间戳。若任一分段或合并失败，不得保存看似完整的半成品会议笔记。

**模型调用失败策略（L41）**：云端模型初始调用失败后，使用同一个已配置模型按指数退避最多自动重试 3 次，即单个任务最多发生 4 次实际调用；所有尝试必须沿用同一任务幂等键。重试耗尽后停止自动处理，不得静默切换备用模型或其他云服务商。已经取得的逐字稿、来源标识与处理状态必须保留，任务写入 `_vault/_signals/model-errors/` 错误队列并发出 macOS 通知；用户可在修复配置、额度或网络问题后显式重跑。失败任务不得生成半成品结构化笔记，也不得产生待确认行动项。

**费用保护（L42）**：每次模型调用记录时间、能力类型、模型 ID、输入/输出 token、重试次数与按当期配置单价计算的估算费用，形成可按日和按月汇总的本地用量账本。配置项提供 `monthly_soft_budget_cny`；达到提醒阈值时通过 `wb status` 与 macOS 通知告警，M2 上线后同步进入简报，但软预算不得中断新会议自动归档。历史补导在开始前必须显示预计会议数、token 与费用；预计执行会跨越软预算或达到配置的高成本阈值时，要求用户再次确认。系统不设置默认硬停机额度，供应商实际账单仍为最终依据。

**转写入口决策（L14）**：

1. 首选飞书视频会议的 **Note（会议纪要）链路**：定位已结束会议取得 `note_id`，读取智能纪要与逐字稿。普通纪要的逐字稿通过 `verbatim_doc_token` 对应的飞书文档读取；统一纪要通过 Note transcript 接口读取。
2. **不把妙记作为主链路**。录制产生的 `minute_token` 及妙记产物仅在租户现有权限与额度允许时作为备用来源，产品可用性不得依赖另购妙记流量。
3. 若某场会议没有 Note、API 权限不足或实际租户无法读取，自动降级为本地投递文件夹或命令导入，不得让会议知识链路整体阻塞。
4. M0 必须用本人租户中的一场真实历史会议完成 API 冒烟测试：能够从会议定位到纪要，并取得至少一种完整文本产物。通过后启用 API 自动拉取；未通过则按本地入口交付，并在 `wb status` 中显式显示降级状态，M2 上线后再同步显示于简报。
5. 通过 `launchd` 每 30 分钟查询新产生且未处理的会议纪要，并提供手动触发命令。禁止为此新增常驻 WebSocket 监听或服务端进程。
6. MVP 仅 Mac Studio 触发，但处理任务仍必须以 `meeting_id + note_id`（本地导入时使用内容哈希）作为幂等键；发现 vault 中已有成功记录即空转，避免重复笔记与重复模型调用，并为未来接入 Mac Air 保留防重能力。
7. 自动发现范围是本人参加且以 `user_access_token` 有权读取完整逐字稿的全部已结束会议，不要求本人主持或发起，也不在下载前按项目过滤。无完整文本权限的会议记录为 `unavailable` 并显示原因，不得用标题或飞书摘要冒充完整处理结果。
8. 上线后只自动处理新发现的会议。历史会议通过显式命令按日期范围补导，例如 `wb meeting backfill --since YYYY-MM-DD --until YYYY-MM-DD`；命令必须先显示预计会议数，再开始调用模型。
9. 历史补导按会议逐个提交与记录进度，支持中断后续跑；已完成、不可用和失败会议分别记录状态，重跑只处理未完成或用户明确要求重试的失败项。禁止默认全量扫描和处理全部历史会议。
10. 历史补导默认仍生成完整逐字稿与结构化会议笔记，但不把其中的行动项写入当前待确认页。仅当用户显式添加 `--include-actions` 时才生成候选；这些候选必须标记 `historical` 与会议日期，仍需逐条确认后才能写回。

### 3.2 AI 工作台侧

#### 3.2.1 Prompt 管理

- 位置：`SummitWorkbench/prompts/`，随 git 版本化
- 每个 prompt 单独文件，文件名即用途（`brief-ranker.md`、`session-wrapup.md`、`inbox-router.md`、`meeting-processor.md`、`weekly-review.md`、`vault-qa.md`）
- 变更走 git commit，可回滚
- **禁止在脚本中内联 prompt 字符串**

#### 3.2.2 支持接入的模型

| 场景 | 模型 | 说明 |
|---|---|---|
| 环 B 交互式会话 | **本期不实施** | M3 不在当前交付边界 |
| 环 A 简报排序 | `ranking_model` | 仅做排序；首版默认候选 DeepSeek V4 Flash |
| 会议转写结构化处理 | `meeting_model` | 首版默认候选 DeepSeek V4 Flash |
| `wb ask` 即时问答 | `qa_model` | 首版默认候选 DeepSeek V4 Flash |
| 每日/每周工作综合 | `review_model` | 首版默认候选 DeepSeek V4 Flash |
| 本地模型 | **不引入** | L33 已确认所有会议内容允许上云，本地模型没有独立职责 |

`meeting_model` / `qa_model` / `review_model` / `ranking_model` 分别配置模型 ID、API base URL、鉴权引用、超时和最大输出长度。首版允许四者指向同一模型，但业务代码、prompt 与输出 schema 禁止写死供应商或模型名称；单项换模不得影响其他能力。

环 B 交互式会话（Codex 或 Claude Code）当前不在交付范围内，不影响环 A 的简报/会议处理和
`wb ask` 的云端模型能力。若未来重启 M3，再另行确定执行器与收尾契约。

#### 3.2.3 上下文拼接逻辑

环 B 拉起 AI 时，按固定顺序拼接（后者不得覆盖前者的约束）：

```
1. 全局约定        _vault/conventions.md
2. 项目档案        <project>/AGENTS.md
3. 项目当前状态    _vault/projects/<project>.md 的「当前状态 / 下一步 / 阻塞」区块
4. 近期相关会议    _vault/meetings/notes/ 中关联该项目的最近 3 条结构化笔记（可配置）
5. 近期工作记录    _vault/logs/ 中该项目最近 3 条（可配置）
6. 本次任务指令    用户输入或简报条目
```

超长时的截断顺序：先截 5，再截 4 中未确认或低相关内容，再截 3 的「决策记录」，**1 与 2 永不截断**。会议完整逐字稿永不默认拼接，只保留可按需读取的来源链接。

#### 3.2.4 工具调用（Function Calling / MCP）规划

| 环 | 连接方式 | 理由 |
|---|---|---|
| **环 A**（无人值守批处理） | **脚本直连飞书 OpenAPI（HTTP），零 MCP** | 无对话场景，MCP 徒增进程与调试层级 |
| **环 B**（交互式会话） | **MCP**：飞书任务读写 | 有对话、有临时调用，MCP 的正确主场 |
| **会议知识链路** | **飞书 OpenAPI 自动拉取 + 本地文件兜底** | 优先读取 VC/Note 会议产物；实际租户不可用时仍可导入转写文件 |
| Obsidian | **不用 MCP** | 就是本地文件夹，直接读写文件 |
| WorkBuddy | **不接入** | 观测其 inbox 积压数，不发消息、不编排 |

**LLM 能力边界（硬约束）**：

> 环 A 中 LLM 的输出格式**必须**是「条目 ID 的排序数组 + 分组标签」的结构化 JSON，**禁止输出任何自然语言正文**。简报中每一个字（会议标题、时间、任务名、文件路径）都从飞书原始响应与 git 命令结果直接取，不经过模型。

这使模型能犯的最严重错误被限制为「顺序排错」——用户一眼可辨、代价为零。**模型没有物理途径把「3 点评审」写成「4 点」。**

#### 3.2.5 每日与每周工作综合（L25）

| 产物 | 目的 | 最小内容 | 落点 |
|---|---|---|---|
| 每日短反馈 | 维持工作连续性，不增加阅读负担 | 最近完成（精简）+ 今日最多 5 项行动 | `_vault/daily/YYYY-MM-DD.md` |
| 每周跨项目复盘 | 看见跨项目趋势并重新分配注意力 | 本周完成、关键决策、未闭合信号、停滞项目、下周建议 | `_vault/reviews/weekly/YYYY-Www.md` |

两类产物都必须把「可验证事实」与「AI 建议」分区，并为事实附稳定来源链接。每周复盘不得仅改写 7 份每日简报，必须从会议笔记、项目主笔记、工作记录、git 与飞书任务状态重新汇总并去重。

**工作事实三级证据（L26）**：

| 等级 | 展示语义 | 可接受证据 | 禁止行为 |
|---|---|---|---|
| E1 | **已完成** | 飞书任务状态完成；功能分支已合并；会话收尾明确标记完成；inbox 条目已归档；其他可机器验证的闭合信号 | 仅凭一次 commit、会议讨论或模型判断宣称完成 |
| E2 | **正在推进** | 新 commit；未提交改动；经用户确认的会议进展陈述；项目主笔记明确状态更新 | 将“讨论过”“计划做”写成已经推进 |
| E3 | **可能进展 / 待确认** | 模型根据上下文推断，但没有 E1/E2 证据 | 混入事实区、参与完成量统计或自动升级为 E1/E2 |

- 每条工作综合记录必须保存 `evidence_level` 与 `evidence_refs`。
- AI 只能根据输入证据分配候选等级，不能凭自身输出升级证据；E3 升级必须出现新的客观证据或经过用户确认。
- 会议转写中的进展陈述在集中待确认前属于 E3；用户确认后最高可成为 E2，除非同时存在独立的 E1 闭合证据。

**周复盘调度（L27）**：Mac Studio 每周一 07:30（`Asia/Shanghai`）生成上一自然周（周一 00:00 至周日 23:59）的复盘，并在 08:00 晨间简报生成前提交到 vault。幂等键使用 ISO week（`YYYY-Www`）。主机在计划时间休眠时，下一次唤醒执行补生成；08:00 简报等待一个有上限的短窗口后仍未取得周报则照常生成并标注缺失，不得无限阻塞。

**周建议进入行动排序（L28）**：当前周复盘的「本周建议」自动进入晨间简报的提议候选池，可竞争混合配额中的「主线推进」名额。每条必须标记 `proposal`、链接来源周报并列出依据；不得因此修改项目主笔记、创建飞书任务或改变 E1–E3 证据等级。新一周生成周复盘时重新评估候选，不把上一周建议无条件滚动。

#### 3.2.6 第二大脑即时问答（L29）

基础入口：`wb ask "<问题>"`，可选项目与候选条数。处理顺序固定为：路由判定（点查 / 综合 /
回溯 / 决策 / 回顾）→ 按 profile 的 type/status 过滤 → 块级 FTS5 + BM25 召回 → 多信号融合 +
双链扩展 → 控制上下文长度 → 调用配置的云端模型 → 输出带 `路径#区块` 引用的回答。

候选条数由**路由计划**决定（`workflows/ask/router.routed_limit`）：CLI、验收脚本与 App 面板
共用同一口径，不再各自写死默认值（T4 修掉的缺陷）。索引不可用时退回纯 Markdown 子串扫描，
并在检索轨迹里写明降级原因。

硬约束：

- 每个事实性结论必须引用至少一个实际输入模型的本地 Markdown；不得引用未进入本次上下文的文件。
- 「发生过什么 / 已决定什么」与「建议接下来做什么」必须分区回答；建议不得伪装成历史事实。
- 证据冲突时并列展示冲突来源及日期，不能擅自选一个为真；证据不足时明确回答无法判断。
- 默认不保存问答正文。仅在用户显式使用 `wb ask --save` 时写入 `_vault/insights/`，并记录原始问题、回答、实际输入来源、模型 ID、prompt 版本与生成时间。
- 保存的问答使用 `type: qa-insight` 与 `status: generated`，属于派生洞察，不得作为 E1/E2 事实证据。`wb ask` 的事实检索默认排除 `qa-insight`，避免模型回答相互引用形成事实循环；用户明确查询“以前的分析/建议”时才可纳入，并必须标注其派生性质。
- vault 中符合检索条件的工作材料均可进入已配置的云端模型上下文；不做 `local-only` 分路或本地模型二次处理。

#### 3.2.7 Web 工作台（本地便利层，L45–L52）

`wb web` 是 CLI 的**本地按需便利层**（非必要组件、不改变数据边界）：SPA「今日工作台」+ 审批页 + JSON API；桌面 App 的受管 WKWebView 加载的也是同一套面板。设计说明见 [docs/product/WEB_WORKBENCH.md](WEB_WORKBENCH.md)，操作指南见 [docs/product/WEB_USAGE_GUIDE.md](WEB_USAGE_GUIDE.md)。核心约定：

- 「今日」页自上而下：快速捕捉（AI 分类，L47）→ 待确认审批卡片（积压置顶）→ 会议逐字稿拖拽导入（全自动，L46）→ 项目推进卡（未提交/落后/下一步，含**知识线程**）→ **晨间简报（v2 组件化日程视图，L49）** → 问答。
- 晨间简报 v2 只重排**面板内的呈现**：会议时间列 + 任务截止语义色/倒计时 + AI 优先注解（与待办清单合一，L49）；vault 当日笔记里的简报 Markdown（§4.1 环 A 产物）保持版式不变，是 Obsidian 侧与 G1 回归的唯一真源。
- **线视图（v0.4，L51）**：点项目/线程名打开 = 档案区块（当前状态/下一步/阻塞/跟进事项/决策记录）+ 时间线聚合（logs/artifacts/meetings）；视图内可直接「✎ 日志 / 存产物 / 刷新」；线程卡 >14 天无更新显示「⚠ N 天未更新」（L52）。
- 「审批」页与 CLI 共用同一份 `meetings.md` 事实源：即时批准/拒绝/修改 + 预演/应用；批准写回仍须逐条确认（L13）。目标项目下拉覆盖已建档知识线程（L50）；落点含「跟进事项」（他人行动项 → 主档案 `## 跟进事项`，v0.4）。
- 所有页面数据来自 `/api/*`，与 CLI 读同一套 repositories/workflows；未构建前端时自动回退服务端渲染，功能不缺失。

## 5. 非功能需求（NFR）

### NFR-1 性能

| 指标 | 目标 | 说明 |
|---|---|---|
| 简报端到端生成时长 | **P95 ≤ 5 秒** | 从 launchd 触发到笔记落盘 |
| 其中 LLM 排序调用 | ≤ 2 秒 | 单次调用，结构化输出 |
| 本地项目扫描（4 个） | ≤ 500ms | 纯 git 命令 + 文件读取 |

> **关于 TTFT**：本项目不自建推理服务；环 B 交互式会话当前不在交付范围，因此不设其 SLO。可控的是简报端到端生成时长，以上文为准。

### NFR-2 准确率评估方案

| 层级 | 方法 | 频率 | 阈值 |
|---|---|---|---|
| 事实区 | 自动化回归：mock 飞书响应 + 固定 git fixture，比对渲染输出 | 每次代码变更 | **100% 一致** |
| 事实区 | 人工抽查：比对当日简报与飞书 / git 真实状态 | 每周 7 份 | **零错误** |
| 提议区 | 人工标注 20 样本（有用 / 无用 / 错误） | 每月 | 有用 ≥ 60%，错误 ≤ 10% |
| 上下文 | 统计环 B 会话中需人工补背景的比例 | 每月 | ≤ 20% |

**事实区任一错误即视为 P0**，回滚到上一版本模板。

### NFR-3 单主机 MVP 与未来 Mac Air 接入

| 项 | 方案 |
|---|---|
| MVP 运行主机 | **Mac Studio**。定时任务、飞书拉取、云端模型调用与写回均只在该机部署和验收 |
| Mac Air 定位 | 后续出差端；MVP 不安装定时任务，也不进入当前验收 |
| 工作项目根目录 | 统一约定为 `~/Documents/Work/`，当前先在 Mac Studio 落地 |
| 一致性机制 | **git remote 为唯一真源**；`work-sync` 脚本遍历 `~/Documents/Work/*` 批量 pull/push。即使 MVP 单机，也不得把本地目录当作不可迁移的唯一副本 |
| **禁止事项** | **严禁用 iCloud Drive / Dropbox 同步含 `.git` 的目录**。iCloud 会将文件 evict 为 dataless 占位符，`.git/objects` 下大量小文件被 evict 后 git 读到不完整数据；两端各有未推送提交时按单文件粒度合并 `.git/index` 与 `refs/` 将直接损坏仓库 |
| vault 同步 | `_vault` 本身是独立 git 仓库（私有 remote），与工作项目同机制 |
| 定时任务防重 | MVP 虽为单机，仍保留稳定幂等键与重跑守卫，防止 launchd 重跑并为未来多机接入做准备 |
| 项目清单 | 简报纳入范围 = Mac Studio 的 `~/Documents/Work/` 下**且**根目录有 `AGENTS.md` 的项目 |
| **路径硬编码** | **所有脚本禁止硬编码 `/Users/<name>/`**，一律用 `$HOME` 或环境变量 `WORK_ROOT` |

### NFR-4 权限与密钥

| 项 | 规定 |
|---|---|
| 飞书应用 | 自建应用：**日历只读 + 任务读写 + 视频会议/会议纪要只读**；为读取纪要正文，仅申请会议产物所必需的文档只读权限。仍不申请消息、多维表格或通用文档写权限 |
| 身份类型 | `user_access_token`（以本人身份操作本人数据） |
| 密钥存储 | macOS Keychain 或环境变量。**禁止进入任何 git 仓库、禁止进入 AI 对话上下文** |
| Token 刷新 | refresh_token 自动续期；失败时按 NFR-6 显式告警，不静默重试 |
| vault 仓库 | **必须 private**。含飞书任务标题与工作决策 |

### NFR-5 数据外传边界（L6′）

原 L6「飞书业务数据尽量本地」为模糊表述，已修订为**列举式白名单——未列出者一律禁止**：

| ✅ 允许进入云端模型 | ❌ 绝对禁止 |
|---|---|
| 飞书任务：标题、截止日期、完成状态 | 飞书消息正文（未申请该权限） |
| 飞书日历：事件标题、起止时间 | 与会议产物无关的飞书云文档正文 / 多维表格数据行（未申请） |
| 全部会议：智能纪要、完整逐字稿、说话人、时间戳 | 飞书原始录制视频（二进制不下载、不发送模型） |
| 本地代码、Obsidian 笔记内容 | App Secret / access token / 任何凭据 |

**已知残留风险（明示，不做隐瞒）**：任务标题与会议逐字稿天然包含同事姓名、发言内容及可能的第三方信息，此边界涉及**第三方个人信息外传**。用户已明确确认不存在需要本地隔离的敏感会议，全部会议内容允许发送给已配置的云端模型；MVP 不脱敏、不引入本地模型，但此风险已知悉并记录在案。

### NFR-6 失败可见性

> **任何静默失败都是本项目的头号敌人**——一个不再运行却无人察觉的简报系统，比没有系统更糟。

| 场景 | 处理 |
|---|---|
| 飞书 API 调用失败 | 简报采集失败时照常生成并标注对应区块；会议拉取失败时写入状态、由 `wb status` 展示并通知，保留本地导入兜底 |
| 某项目扫描失败 | 该项目标注「⚠️ 扫描失败」，不影响其余项目 |
| 云端模型调用失败 | 初始调用失败后，同一模型指数退避重试最多 3 次；仍失败则保留原始材料、写入 `_vault/_signals/model-errors/` 并发出 macOS 通知，不自动换模型 |
| 会议待确认项积压 | M1 由待确认页与 `wb status` 显示数量，M2 起同步显示在简报；达到 5 条或最老超过 3 天时发出 macOS 通知，只在跨越阈值或告警升级时重复提醒 |
| 简报整体生成失败 | macOS 通知告警 + 写入 `_vault/_signals/error-YYYY-MM-DD.log` |
| 连续 3 天生成失败 | 通知升级为强提醒 |
| 连续 7 天无工作活动信号 | 简报首行提示检查采集健康度；判定范围包括会议、任务、git / 项目文件变化与手工录入，不能仅因用户没有手工录入而告警 |

### NFR-7 隐私与部署

- **产品程序在 Mac Studio 本地运行**，不自建服务端、不对外暴露端口；“本地运行”不等于“本地推理”，所有模型能力仍调用 NFR-5 白名单内的云端模型 API
- 唯一外部调用：飞书 OpenAPI + 云端模型 API（范围受 NFR-5 约束）
- MVP 简报与 vault 存于 Mac Studio 与私有 git remote；未来可把 Mac Air 接入同一 remote

### NFR-8 模型用量与费用可观测性

- 所有云端模型调用均须进入本地用量账本，区分 `meeting_model`、`qa_model`、`review_model` 与 `ranking_model`，并能追溯到对应任务幂等键。
- 估算费用使用可配置模型单价计算；单价或模型变更不改写历史记录，避免历史账目随配置漂移。
- 月度预算是提醒线而非停机线：达到阈值后必须显式告警，新会议仍继续处理。
- 批量历史补导属于可推迟开销，跨越预算或高成本阈值时必须二次确认后才执行。
