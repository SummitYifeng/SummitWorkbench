0总则（一句话就够）

原件进 sources/（逐字、不可改），结论进结论层（对象页 / 事件页 / 分析笔记 / 主题簇页）。 一页只讲一件事；小标题要能被人读懂；不确定就先入后改。
为什么原件要逐字

「他当时说的是『尽量』还是『必须』」会决定后续判断。改写过的原件，之后所有引用都指向二手件。

为什么结论要分层

问答时只依据召回内容作答。结论层能被精确定位到「哪一节」，原件只作证据。

为什么要小标题

库按 #/## 切块。### 不算块边界——长文档若只到三级标题，整篇只能算一个块，无法定点引用。

5入库前自检（勾一下就知道能不能入）

还不能入库

前 3 项是「检索能不能用」的关键；后 3 项是「以后能不能维护」。不必全绿才入——第 6 项不满足时， 把总结挪到结论层页即可，原件保持逐字。

6不完美怎么办

你说过「归档进去的都不是完美版本」——这本来就是设计前提。

先入，再迭代

缺东西就在正文写 <!-- 待补：… -->，或列进 ## 未决问题。别为了等完整而不入——不入库的信息等于不存在。

想能检索，就别用 draft

status: draft 不进问答索引。只在「确实不希望被引用」时才用；平常都用 active。

有新增就追加到原页

同一个人 / 同一个对象的后续沟通 → 加进它的 ## 时间线 一行。不要新建一篇「补充说明」。

推翻旧结论不改旧文

新写一篇、旧篇 status: superseded，两篇在 ## 关联 互链。原件永不修改。

7常见错误（对照检查）

❌ 别这样✅ 应该这样
把三个月的记录塞进一个 XX全部记录.md一次事一个文件；同一对象的后续追加到对象页时间线
把「我的总结」写进原件原件逐字放 sources/，结论放对象页 / 分析笔记
原件 / 手记只写到 ###，或干脆没有小标题用 ## 分节——只有 # 与 ## 会被切成块，### 不算；想让某一节被精确引用就写到 ## 这一级
一份文件里混着「定稿 + 过程稿」过程稿另起一节，并写明哪个是最终版
文件名带「最终版」/ V2状态用 status 字段表达，文件名保持稳定
只写在桌面 / 备忘录 / 微信直接写在 vault 对应目录（否则检索永远看不到它）

8节奏

复盘 · 当天或次日

记忆衰减最快，晚一天少一半信息。5 行就够：上午效果 / 下午效果 / 做对了什么 / 下次改 3 件事 / 要不要继续某个做法。

手记 · 攒批

每周或每完成一件事集中补，不必当场开对话。

会议稿 · 开完就导

导入后到审批页裁决；只保存文件不会写回，要点「应用（写回）」。

9什么时候交给我更划算

你自己做更快（而且下一次提问就能检索到）。这三类例外：

① 大文档原件归档

要逐字粘贴 + 算哈希 + 写要点 + 回链。15KB 的文档手工做很痛苦。

② 需要跨页回填

新建决策页要同时动台账、项目页、索引——一套动作，容易漏。

③ 一次 3 份以上

批量入库有幂等键与去重判断，交给我不容易乱。

另外：任何你觉得「结构上拿不准」的，直接问。改结构要连规范、模板、库三处一起动，这是我的活。
