# SWB 文件夹工作台改造与四阶段验收计划

本文供 Luna 串行执行：先交付新版 SWB，再选择性建立 OneDrive 工作库与样板，之后验收两台 Mac 的交替使用，最后适配 SK 并验证检索。产品目标是收敛用户操作，保留独立可读的 Markdown 资产，把文件同步交给外部工具。

日期：2026-10-02。核对源码基线：`c89677cc8f73ec9bc6f7f5b297f44f9f4db66d1e`，项目版本 `0.4.11`。已发布基线仍以 AGENTS.md 中的 `6253d31` 为准。本文是下一版的实施目标，不是现有功能已经完成的声明。本次只制定计划；没有修改真实工作库、调用模型、创建飞书任务或执行发布。

## 1 产品与实施范围

SWB 是 macOS 上的个人工作台，负责收集工作输入、整理内容、人工确认、知识落盘、项目更新与飞书动作。SK 负责只读检索、向量化、精排和问答。OneDrive 负责文件同步。三个系统分别安装、配置和验收。

适用用户：同事的单机个人库，以及使用者的 Mac Studio M3 Ultra / Mac Air M4。两台 Mac 交替使用，同一个库只有一个写入设备。同事各有自己的库，本期不支持多人共写。

用户的三个主要输入入口为「记点什么」「导入会议」「存入文档／产物」。日常手记、工作思考保留为录入快捷模板；项目更新、编辑已存内容保留为上下文操作。审批只显示三个业务去处：「沉淀知识」「更新项目」「创建飞书任务」。目录、文件类型、规范字段由 SWB 管理。

### 1.1 已确认的产品规则

| 范围 | 下一版行为 |
| --- | --- |
| 工作库 | 用户选择的本地文件夹，默认名称 `_vault`，可以使用其他名称；既支持普通本地目录，也支持 OneDrive 目录 |
| 首次安装 | 新建专用库或连接可识别且兼容的 SWB 库；完成工作库、模型、飞书配置后进入工作台；飞书应用凭据内置，用户完成自己的授权 |
| 普通已有文件夹 | 非空且没有 SWB 契约的普通 Markdown 文件夹不直接接管；内容经后续导入进入新库 |
| 文件夹切换 | 设置中重新选择；当前任务完成后切换；任务始终绑定原工作库；软件不负责移动文件 |
| 契约 | 新库初始化即生成身份与通用契约，未安装 SK 也一样；版本不兼容完全拒绝打开，不进入部分只读工作台 |
| 配置 | 飞书身份、模型及密钥属于本机 SWB；换库不切换账户或模型；换机各自授权和配置 |
| 工作模式 | 应用按需运行；取消主设备／副设备与 Studio 常驻写入的产品模型；不建设离线优先能力 |
| 模型调用 | 保存输入、列表、打开卡片不调用模型；只有明确的整理／处理操作调用；支持用户手工整理 |
| 内容确认 | 所有正式知识，包括手写记录、产物与项目正文变化，都需确认；零散输入可合并，也可暂存或舍弃 |
| 审批粒度 | 一组来源对应一张结果卡，分别选择三个去处，默认全部不选；一次明确提交，分别显示结果 |
| 外部动作 | 内容批准与飞书任务批准独立；已成功动作不重做，结果未知先核查，不能盲目重发创建请求 |
| 检索资格 | 仅当前内容版本已批准的正式内容可进入 SK；逐字稿、原始资料、收件箱、草稿和机器状态排除 |
| 内容修改 | 已批准内容变化后重新确认；应用内可「保存并确认」；外部编辑即使尚未被 SWB 扫描，也不能由 SK 继续当作已批准内容使用 |
| 文档产物 | 保留全文；AI 整理可选；保存产物与修改项目当前状态分别选择，不自动用摘要覆盖项目 |
| 事实边界 | 项目事实、业务决定、任务必须来自输入；思考笔记可含明确标识的推断、假设和问题；不制造会议结论或业务决定 |
| 简报与周复盘 | 保留，依据确认后的工作内容和飞书信息；程序生成的展示内容不自动进入正式知识库 |
| 同步与备份 | 用户通过 OneDrive 客户端检查交接；SWB 不调用 OneDrive 同步 API、不声称云端同步成功；备份使用已有工具，SWB 提供恢复说明 |

### 1.2 明确移除与暂缓

从工作库功能中移除 Git commit / push / pull、代理与 SSH 配置、冲突合并面板、Git 撤销历史、主副设备接管，以及工作源码仓库扫描。SWB 源码仓库自身继续使用 Git；两者不能混淆。

本期外部审批执行去处收敛为飞书任务。飞书日历／任务的已有读取和直接操作需要盘点保留；任何已有日程创建等功能的保留或退役，应在工作包 W0 的功能清单中逐项写清，不悄悄扩成第四个审批去处。

其他办公软件连接、音频转写、PDF/OCR、多人编辑、同步引擎、通用备份引擎、自动语义聚类和 SWB 内的检索问答不纳入本轮。文本导入先保留 `.md/.txt` 与粘贴。

### 1.3 日常网络边界

验收目标是两台 Mac 在使用者的国内网络、不开代理时，能访问所选模型、飞书和 OneDrive。用户已有 OneDrive 直连使用经验，实际可用性仍由第三阶段验收。

GitHub 不再是日常工作流依赖。现有应用更新渠道可能仍指向 GitHub，W0 必须盘点：本轮先交付本地 DMG 并关闭默认的 GitHub 自动检查／下载；设置保留手动安装说明。国内静态更新渠道可另立任务，不为这一轮新增托管服务。不开代理不等于模型数据或 OneDrive 数据必须存于中国境内，后者不属于本轮已确认要求。

## 2 四阶段顺序与门槛

| 阶段 | 交付物 | 通过后才能进入下一阶段 |
| --- | --- | --- |
| 一 SWB 改造 | 新契约、收敛后的录入审批、无 Git 写入链路、跨设备必要状态、带飞书应用凭据的安装包、单机验收报告 | 全部写入入口受相同规则约束；普通本地目录端到端可用；故障恢复与打包验证通过 |
| 二 新工作库与样板 | OneDrive 新库、选择性导入清单、几个完整项目样板、日常使用说明、单机样板验收报告 | 内容已由用户确认；来源完整、链接可解析；原库未被移动／覆盖；Studio 新库实际可用 |
| 三 第二台 Mac | Air 新装与 Studio → Air → Studio 交接报告、代理关闭下的服务结果、状态连续性与幂等证据 | 相同库身份、待办和回执可延续；没有重复模型处理或重复任务；两端内容一致 |
| 四 SK 适配 | 新库接入、版本审批过滤、增量索引与失效清理、向量／精排／引用验收报告 | 未审内容和原件不召回；旧向量不会泄漏；精排实际执行；引用可追溯；真实测试费用有记录 |

第一阶段冻结 SWB ↔ SK 的接口与测试样例，第四阶段再修改 SK 实现、调用嵌入服务并调优。在第四阶段通过前，不把新库接入旧 SK，也不让旧索引承担新库检索。这避免为配合旧规则而先产生错误语料。

样板既是第二阶段的人类使用范例，也是第四阶段的固定检索验收集。第三阶段测试 SWB 和文件同步，暂不把 SK 检索算入验收范围。

## 3 Luna 的执行规则

1. 先读取根 AGENTS.md、当前源码、真实工作库 `conventions.md`，随后核对本计划。用户本轮确认的新产品要求优先于旧架构文档；旧 archive 内容保留原文。
2. 按 W0 至 W8 串行完成。每个工作包交付：变更文件、通过的验收项、命令与提交身份、已知缺口、下一包前提。不要把所有模块一次重写。
3. 默认在隔离测试库中开发；第一阶段不修改 `/Users/yifengair/Documents/Work/_vault`，不连接运行中的旧 App 做写入验证，不推送它的 Git remote。
4. 不启动 SK 全量重嵌来验证 SWB。模型、飞书创建和 OneDrive 网络故障用替身测试；真实调用只在相应的人工验收中执行并记录。
5. 不在代码、计划、日志、fixture 或提交中放入 App Secret / token / API key。打包凭据沿用 RELEASING.md，不打印值。
6. 只在工作包边界运行必要的验证；新功能失效、重试或发生新修改时再扩测。不通过删除关键守卫、放松覆盖率或统一跳过测试来交付。
7. 实际代码提交、发布、安装、迁移及收费验收的状态分开记录。不能把「源码测试通过」写成「用户装机通过」，也不能把「文件已写入」写成「OneDrive 已同步」。

## 4 第一阶段的工作包

### W0 冻结接口与功能盘点

交付：下一版产品规格、共享契约草案、所有读写入口清单、退役清单、最小样例库。先在仓库内写草案和初始化模板，不改真实旧库契约。建议下一版使用 `0.5.0`，版本号在发布工作包确认。

盘点至少包含 Web／CLI／原生壳／定时任务中的 capture、journal 两入口、会议导入与后台处理、inbox promote、产物、项目新建／状态／归档、review apply、简报、周复盘、外部动作、设置、升级和恢复。每条记录其模型调用点、写入文件、审批要求、外部副作用、旧 Git 依赖；任何保留写路径不得遗漏。

契约必须冻结以下内容，提供机器可校验的有效与无效样例：

- 沿用既有 `workspace_id` 作为可携带的库身份，不从绝对路径推导；新库使用新身份。库身份、契约版本、最低读写版本在 manifest 中声明；不兼容就拒绝打开。
- 正式内容类型、来源类型、辅助目录、审批状态、项目引用、合法锚点；复用现有类型与业务状态，避免重新发明一套目录分类。
- 审批采用独立的版本证明，不能单凭 `status: active/generated/applied` 推定批准；项目归档状态与内容批准状态分开。
- 建议在 Markdown frontmatter 增加 `approval` 对象，包含 `version`、`content_sha256`、`approved_at`、`operation_id`。指纹基于规范化的正文和语义元数据，排除 `approval` 自身；编码、换行、字段排序及参与字段白名单在本工作包固定。名称和规则冻结后两端使用相同测试向量。
- 至少覆盖正文、标题、摘要、类型、项目归属、业务日期、业务状态、业务决定及替代关系的变更。批准时校验当前版本与预览版本一致；外部编辑和审批期间发生的修改都不能沿用旧批准。
- 自动统计的活动时间等信息放辅助状态，不自动重写已批准的业务正文／语义元数据。若业务字段真的改变，应随该次确认生成新批准证明。
- 正式内容检索资格是「允许的类型 + 允许的业务状态 + 当前版本批准证明匹配」；缺字段、未知类型、无效指纹默认排除。原件即使带批准字段也不进语料。
- 原始来源、正式产物与派生总结分别定义；保留完整产物不等于把原始逐字稿转换成可检索产物。

通用模板不包含使用者的八个真实项目、个人邮箱或账户。需要项目时由用户建立；工作流字段提供通用默认值。新库必须包含可读 `conventions.md`，§9.1 与仓库共享契约草案一致；第三方同事的新库不依赖使用者原库路径。

完成标准：一份已批准会议、一份未批准手记、一份改动后的产物、一份原件、一份归档但已批准的业务内容，都有明确的预期资格；初始化／兼容性／审批指纹的测试向量可供 SWB 和 SK 复用。W1 开始前不留需要实现者自行决定的审批语义。

### W1 文件夹初始化与本机配置

主要现有落点：`domain/workspace.py`、`repositories/workspace_manifest.py`、`config/profiles.py`、`config/paths.py`、`workflows/onboarding.py`、`webapp/routers/onboarding.py`、`webapp/services/workspace.py`，以及前端设置与首启、原生目录选择流程。核对实际调用链后再修改。

实现：

- 新建库让用户选保存位置与名称；连接库让用户直接选库根。避免自动拼出 `_vault/_vault`。
- 校验路径可读写、可识别、身份和版本合法；不能把没有契约的非空文件夹静默改造成库。普通空目录与专用新目录均可初始化。
- 不要求 `.git`、remote、Git 凭据或 SK；只创建必要通用文件，其余目录按需创建。
- 读取失败或身份损坏不回退为基于路径的新身份，不静默初始化。单篇正文损坏只阻止涉及该页的操作，健康内容继续可用。
- Feishu / LLM 配置和密钥提升为本机应用配置；旧 profile 配置做一次显式兼容迁移，旧文件保留可恢复。遇到多个账户配置不得随便选择或覆盖。
- 切换库前停止接收新任务，等待当前工作结束。长任务绑定库身份及开始时的路径，不读切换后的全局配置；未解决的外部动作有可恢复的记录后才能离开。
- 库目录由 Finder 移动后可在设置重连，同一身份的待审状态继续有效。取消首启与目录选择不会留下半个新库或半切换配置。

完成标准：全新单机库、已有兼容库、无契约非空目录、损坏 manifest、版本不兼容、目录搬家、切换时有任务、模型／飞书暂时失败等路径均有明确结果。服务短暂不可用只影响对应功能。

### W2 文件写入与跨设备必要状态

主要现有落点：`webapp/mutation_runtime.py`、`workflows/local_mutation.py`、`repositories/_atomic.py`、`repositories/external_action_outbox.py`、`repositories/meeting_state.py`、`repositories/meeting_import_jobs.py`、`repositories/review_audit.py`、`repositories/thread_activity_events.py`，及其调用方。

实现：

- 保留单一 mutation 入口、路径检查和本机进程互斥；移除其 Git 状态门禁、commit 与 push。锁根不再依赖 vault 的父目录是 Work 仓库集合；本机锁置于程序目录并以库身份区分。
- 写入前完成 schema、目标路径、批准版本、来源和预览版本校验。继续复用已有 Markdown 渲染器及写回器，避免两套正式落盘实现。
- 单文件使用原子替换。需要改动多个文件的本地业务操作先记录操作 ID、预期旧版本和目标内容，再写入并留下完成回执；启动时可恢复中断操作。恢复不能覆盖期间已改变的文件，应定位到相关操作供处理。
- OneDrive 的跨文件到达顺序不等于事务提交。缺来源、缺状态或尚未齐全的结果只暂停涉及该条目的操作，绝不能推定它已完成或重新创建飞书任务。
- 将待整理输入、整理结果、待审批卡片、会议去重／处理状态、执行账本、完成回执放在库内隔离的 `.summit-workbench/` 辅助区域；全部排除语料。已有 `_events/` 活动记录先盘点，明确保留为辅助来源或一次迁入，不能双写出两个真源。
- 对跨设备必要账本优先复用已有「单条不可变 JSON 文件」原语，记录业务范围、稳定 ID 和状态变更；本机缓存可重建。不把共享 SQLite 或跨端共同追加的单个 JSONL 当作云同步真源，不建设通用事件溯源框架。
- 每个结果、目标动作和请求版本有稳定标识。保存知识／更新项目／飞书动作分别记录结果；卡片重复提交、重启或换机只处理尚未完成项。
- 飞书请求必须先持久化意图，再发请求，最后记录远端 ID／回执；沿用现有 outbox 的结果未知规则与账户范围。出现未知结果禁止自动重发 POST。
- 可携带账本保存非秘密的目标账户引用；新机器当前飞书用户与动作所属用户不匹配时，暂停该外部动作并提示正确授权，不改写账户后继续执行。
- 密钥、用户授权 token、本机绝对路径、进程锁、调试日志、缓存及向量库不进入同步账本。程序生成的简报／周复盘保留本机目录存放，可根据同步内容重新生成。

完成标准：不带 `.git` 的库完成所有保留写路径；各本地写阶段模拟中断后可恢复；重复提交只落一份结果；未知远端结果不重发；同步顺序变化不造成重复执行。测试同时证明 secrets 和本机路径没有进入可携带文件。

### W3 收敛录入与整理流程

主要现有落点：`webapp/routers/capture.py`、`journal.py`、`inbox.py`、`meetings.py`、`threads.py`；`workflows/capture.py`、`workflows/meetings/`；`repositories/inbox.py`、`thread_notes.py`、`thought_notes.py`、`meeting_note.py`；对应前端 today / threads。

实现：

- 三个主入口完成所有常见输入；随手记不强迫选择最终类型或项目。日常手记和工作思考的结构化表单作为快捷模板，散乱输入不需要硬凑三段完整论述。
- 支持用户手选多个片段合并成一组，明确显示来源和输入版本。暂存与列表零模型调用；整理按钮说明会调用 AI。会议可用「导入并整理」这一明确动作，不在打开列表时自动处理。
- 手工整理与 AI 整理进入同一结果模型。AI 只给内容和去处建议，不自动勾选目标，不写入正式批准状态。
- 产物导入保存全文；已有成熟产物预览后可直接确认，AI 摘要可选。不能因有摘要就自动成为已批准内容。
- 会议逐字稿和参考原件逐字保存、不参加检索；待审批的结构化内容允许先落盘，但明确标记待审且无有效批准证明。
- 事实、任务、项目变更和业务决定必须带来源；思考中的分析和假设明确分区。继续遵守「会议笔记不生成 AI 建议」及「决策页只记业务结论」。
- 已成功模型结果随库保留，打开／换机／重复整理同一版本不再默认花钱。用户明确重整或输入改变时可以再调用。模型响应丢失而结果未知时不得声称没有费用，提示用户后再决定是否重试。

完成标准：一句话、散乱多条、完整日常记录、会议、全文产物、项目正文修改各走通。只保存／看列表／预览已有结果时替身模型调用次数为零；用户明确整理一次有可核对的调用与结果记录。

### W4 统一审批与独立执行

主要现有落点：`domain/review.py`、`workflows/review_apply.py`、`webapp/routers/review*.py`、`web/src/features/review/`、`web/src/features/today/inbox.ts`、`web/src/features/threads/artifact-modal.ts`。

实现：

- 一张卡片包含来源、拟保存正文、项目变更前后对照、拟创建任务。目标最多三个，均不预选；批准的是具体版本，不是一条永久授权。
- 提交按钮列明本次动作，例如「保存笔记并创建 2 个任务」。未选择任何去处时不执行，可保留或忽略输入。
- 内容批准不依赖是否有任务。没有任务的会议可以正式保存；拒绝全部任务不能自动把会议正文视为已确认。
- 项目更新只写用户预览过的字段／区块。保存产物与摘要覆盖项目状态分开，禁止默认覆盖。
- 「保存并确认」绑定当前正文指纹；若预览之后内容变化，返回重新预览的提示，保留用户修改。
- 每个去处分别显示成功／失败／待核查；局部成功保留，失败项可继续处理，未知结果先核查。禁止用一个总失败标签促使用户重跑已经成功的动作。
- 同一来源可产生多个不同结果，但不自动把全文复制到日志、思考、产物和决策各一份；保留一个主内容并用关联和短摘要衔接。
- 来源只有在所选结果全部解决或用户明确结束处理后才从待处理队列移出；尚未结束的卡片能显示已完成项，继续操作不会重复写回。
- 保留飞书日期控件，开始／截止日期缺失提示，以及现有完成任务的幂等行为。直接完成已有任务属于明确业务操作，不强迫生成知识笔记。

完成标准：三种单一去处、任意组合、零任务会议、全部任务拒绝、局部成功、重复点击、编辑后批准、过期预览和错误账户均有行为验证。

## 5 第二阶段 建立 OneDrive 新库与样板

前提：第一阶段安装包和单机验收通过。此阶段另行实际执行，本计划不先移动原库。OneDrive 新库的准确本地路径通过用户选择取得，不猜个人账户文件夹名称。

实施顺序：

1. 停止旧 SWB 的写入与定时任务，保留原 `_vault` 及其 Git 历史，完成独立备份。旧库作为迁移来源，新库使用不同身份；旧 App 不连接新库。
2. 在 Studio 的 OneDrive 本地目录由新版 SWB 创建新库，确认文件确实可在本机读取。将整个库设置为始终保留本地下载；在 Air 重复该设置的实际结果留到第三阶段验证。
3. 生成只读导入清单，先由用户选择少量真实项目与材料；暂不整库搬运，不默认全量正式化。
4. 建立三个建议样板：会议推进项目、PRD／阶段产物项目、日常记录／思考项目。具体业务项目和真实文本由使用者选择，范例不伪造业务事实。
5. 每个样板有项目主页、少量确认后的正式内容、可回溯来源和清楚的下一步；另保留一个待审内容，示范它与正式知识的区别。
6. 补齐选择范围内的链接依赖；必要原件以来源类型保留。建立旧路径 → 新路径映射，检查不存在只链接到旧 Mac 绝对路径的引用。
7. 用短篇使用说明说明输入、整理、确认、三个去处及换机步骤。建库方法与测试报告放仓库文档，项目正文和决策页只写业务内容。

验收：用户通过 SWB 完成新会议、一组碎片、一份产物和一次项目更新；可打开真实 Markdown 与来源；待审内容明确；保存产物没有自动覆盖项目；重复导入无重复文件；原库保留；OneDrive 客户端显示本机变更处理完成。此时不声称检索可用。

样板文件内容本身应为真实业务知识；“如何使用 SWB”的说明单独存为被排除的使用文档，不能伪装成业务决策或正式可检索产物。

## 6 第三阶段 两台 Mac 交替使用验收

前提：第二阶段的 Studio 样板验收通过。两端安装同一验收包，分别配置模型并完成本人飞书授权；两端选同一个云同步库，但绝对路径允许不同。

| 场景 | 操作 | 必须看到的结果 |
| --- | --- | --- |
| Air 首次连接 | 下载库全部文件后选择库根 | 相同 `workspace_id`；不创建第二个 `_vault`；不要求 Git、remote 或主设备声明 |

最少完成一次 Studio → Air → Studio 的完整往返；异常场景在隔离副本中进行，不用故意弄坏正式库。

人工交接习惯写入说明：结束当前任务，退出当前设备 SWB，查看 OneDrive 已处理完变更；另一端下载完再打开。没有每次启动的确认弹窗，也不声称本机锁能阻止另一台 Mac 同时写入。单写者是使用前提，SWB 不新增跨设备抢锁／主设备选举。

如果模型／飞书返回了网络超时，记录实际请求状态；“没有重复已完成调用”与“未知请求绝不发生重复计费”不同，后者不能保证。异常重试必须有明确状态。

## 8 第四阶段 SK 适配与检索验收

开始前读取 SummitKnowledge 自己的 AGENTS.md 和当前代码。在前三阶段不改它的生产配置、不触发新库自动索引。本阶段实际执行另行记录 SK 基线与安装包身份。

实施顺序：

1. 工作库根目录改为用户选择的 OneDrive 本地库，不以旧绝对路径或 Git 状态确定身份。引用带库上下文，防止与个人库混淆。
2. 共享 W0 的资格测试向量，严格验证正式类型、状态、当前版本批准证明和来源排除；索引前与检索返回前都检查，不能只在 SWB 启动时验证。

4. 原件仅通过合法来源链接供用户追溯，不因点击来源就自动进召回或精排；向量数据库、检索缓存与机器日志留在各机本地。
5. 增量索引按实际内容变化补齐；没有变更时零嵌入请求。新机器首次建索引可能需要费用，先展示或记录范围和预计调用，不为了测试重复全量重嵌。
6. 先用样板集验证向量召回、关键词召回、精排是否实际执行及引用，再根据证据微调参数；不先换模型和重写算法。语义相关性先于权威和时效调整。
7. 两台 Mac 各自配置索引与密钥，分别验收同一新库；SK 不写正文、审批状态或 SWB 账本。

固定验收集建议至少覆盖下列十项，第二阶段即记录对应样板的预期来源与不应出现的来源：

## 9 失败回退与完成证据

新库和旧库隔离，旧库保留。样板导入失败时撤回新库导入批次或恢复独立备份，不覆盖旧库；不得 force push 或修改旧 remote。新库的任何路径、内容变动用映射表和操作回执核对。

新库契约一旦升级，旧 App 不可再写。恢复旧版本应用只连接旧库；新库需对应版本或在副本上进行经过验证的迁移，不能通过降 manifest 版本绕过门禁。

OneDrive 的历史版本／恢复功能不是 SWB 跨文件事务回滚。恢复 Markdown 后需重新校验身份、引用和批准版本；外部任务回执不能随意倒回并重放。遇到丢失的外部执行状态先核查飞书，无法确定则保持待核查。

每阶段在 `docs/acceptance/` 保存报告，至少列：代码与包身份、设备／网络、测试库或正式库范围、操作与预期、实际结果、真实副作用／费用、证据文件和未通过项。密钥、逐字稿全文和敏感业务正文不复制到公共测试证据中。

只有阶段报告中阻断项清零，才进入下一阶段。无法验证的项目如实标「未验证」，不将它计入完成。
