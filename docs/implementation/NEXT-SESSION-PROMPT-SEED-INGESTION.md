## 3. 核心产出：一份「优质素材」长什么样

**判断标准只有一条**：这份材料进库以后，能不能被**切块、寻址、溯源、且不被加工污染**。
`source` 页的契约是「逐字、不可改」，而且已有机械校验（`kb_verify_quotes.py --materials-root` 会逐字比对原件）。

### 3.1 一份素材的最小形态（按重要性）

1. **一个文件 = 一个单位**。不要把三个月、五件不相关的事塞进一个「XX 全部记录.md」——切块后每块都半截。
2. **逐字不改**。原始措辞本身就是信息（「他当时说的是『尽量』还是『必须』」会决定后续判断）。
   **加工、提炼、结论一律放到分析笔记**，不要动原件。
3. **头部自包含**：日期 / 对象（人·组织）/ 场景（会议·电话·邮件·活动）/ 参与人。
   缺了这些，半年后溯源时读不懂，检索也认不出「这是谁跟谁」。
4. **有 `#` / `##` 小标题**。块边界就是 `#` 与 `##`，它决定 `路径#区块` 能不能精确定位到「酒店报价那一节」。
5. **决定与未决显式区分**。原文里明确「定了 X」的才建 `decision` 页；「还没定 Y」写进分析笔记的「未决」。
   不要在事后补编选项——`## 选项` 只写原件里真实出现过的候选。
6. **文件名稳定可预测**：`<日期>-<对象或主题>-<类型>.md`。它一旦进 `source.ref` 就不再改名（改名会让锚点失效）。
7. **同一次沟通的原件与加工件分开建**：原件进 `sources/`，分析和结论进 `notes/`。

### 3.2 会毁掉检索的常见形态（反面清单）

- 只有一个大文件、内部没有小标题 → 块级引用退化成整篇引用，答案无法定点。
- 只有结论没有过程 → 无法回答「当时为什么这么定」「还有哪些候选」。
- 同一份材料换个文件名再放一份 → 幂等键（`ref` + `hash`）能挡住重复入库，但会让人工判断混乱。
- 把「我的总结」当成原件入库 → 后面所有引用都指向一个二手件，逐字校验也失去意义。
- 长表格 / 大段黏贴的聊天记录不做切分 → 单篇贡献几十个块，把别的笔记挤出上下文（历史上踩过：一份 source 贡献 54 块）。

### 3.3 落到库里的样子（C-lite 三件套）

```
1 份 source（逐字、不可改；`## 原文（逐字，未改写）` 之后原样放原件）
+ 1 篇分析笔记（`##` 结论，块级标题要能被人读懂）
+ N 篇 decision（6 固定区块 + 第 7 区块 `## 关联`；只在原件确有明确决定时才建）
```
规范细节见 `_vault/conventions.md` §4 固定区块、§11 入库管线（C-lite）、§13 扩展规则。
幂等键 `source.ref` + `source.hash` **只在** `source` / `meeting-transcript` 页上判。
