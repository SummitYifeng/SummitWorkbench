# SummitWorkbench 开发计划

> 版本：1.0
>
> 状态：可执行
>
> 依据：`docs/product/PRD.md` v1.1
>
> 当前实施状态：**M0 / M1 / M2 已完成**；产品化 **P1-07D、P2-01B 已收口**（Studio + Air 真机往返与 build 24 增量冒烟闭环，见 `PRODUCTIZATION_MULTI_DEVICE_DISTRIBUTION_PLAN.md`）。当前收口 **P2-02** 同步冲突解释与恢复工作台；**M3 尚未开始**。

## 1. 计划目标

本计划将 PRD 转化为严格有序、可以逐项验收的开发工作包。核心策略是先建立本地工作底座，再以“会议进入第二大脑”为第一个端到端产品切片，之后才建设晨间简报、交互式上下文和低摩擦录入。

开发必须满足三个原则：

1. **先证据，后建议**：原始数据和机器可验证状态先落盘，模型输出永远不能覆盖来源。
2. **先归档，后写回**：会议知识允许自动生成，改变项目与任务的动作必须经过待确认页。
3. **逐里程碑封闭验证**：M1 未通过严格验收，不进入 M2；后续里程碑同样先通过自身验收再扩展。

## 2. 技术与运行基线

### 2.1 计划采用的实现方式

| 领域 | 计划方案 | 约束 |
|---|---|---|
| 运行时 | Python 3.12+ | 首次代码批次确认 Mac Studio 实际版本后锁定 |
| 产品形态 | 本地 CLI + 定时批处理 | 不建立服务端，不开放网络端口 |
| CLI | 单一 `wb` 命令树 | 命令必须支持非交互运行和可读错误输出 |
| 调度 | macOS launchd | 会议每 30 分钟；周报周一 07:30；简报每日 08:00 |
| 数据 | Markdown + 小型 JSON 状态/账本 | vault 内容可读；运行状态可审计；不引入数据库 |
| 飞书连接 | 直接调用 OpenAPI | 后台链路不使用 MCP，不申请 PRD 外权限 |
| 模型连接 | 供应商无关适配器 | 四类模型能力分别配置；首版可指向同一模型 |
| 凭据 | macOS Keychain 或运行时环境 | 不进入 Git、日志、fixture 或模型上下文 |
| 测试 | 单元、契约、集成、验收四层 | 外部 API 默认使用 fixture；真实调用仅用于显式验收 |

具体第三方库及版本不在本次基线中决定。首次代码批次应优先证明：CLI 可打包、HTTP 可替换测试、schema 可严格校验、Keychain 可读、launchd 可调用同一入口；验证后再写入依赖锁定文件和 ADR。

### 2.2 模块边界

| 目录 | 责任 | 禁止事项 |
|---|---|---|
| `src/summit_workbench/cli/` | 命令解析、退出码、面向用户的结果呈现 | 不承载业务规则 |
| `src/summit_workbench/config/` | 配置加载、路径解析、凭据引用 | 不输出秘密值 |
| `src/summit_workbench/domain/` | 领域类型、状态机、证据等级、路由与预算规则 | 不直接访问文件或网络 |
| `src/summit_workbench/providers/feishu/` | 身份、会议、纪要、日历和任务 API 适配 | 不写 vault |
| `src/summit_workbench/providers/llm/` | 模型调用、token 估算、结构化输出校验 | 不写死供应商专属业务逻辑 |
| `src/summit_workbench/repositories/` | Markdown、状态、错误队列、用量账本读写 | 不决定行动优先级 |
| `src/summit_workbench/workflows/` | 编排端到端用例 | 不绕过领域规则和审批边界 |
| `src/summit_workbench/observability/` | `wb status`、日志、通知、预算和积压告警 | 不静默吞错 |
| `src/summit_workbench/scheduling/` | 幂等触发、补跑和 launchd 协调 | 不实现常驻进程 |
| `prompts/` | 独立、版本化的模型提示词 | 禁止在业务源码内联 prompt |
| `templates/vault/` | 稳定的 Obsidian 输出模板 | 固定标题和 frontmatter 不得随意变化 |
| `tests/` | 四层测试与去敏 fixture | 禁止真实凭据和真实会议原文 |

## 4. B0 · 无代码基线

### 4.1 本批交付

- 根目录 `README.md` 与 `PROJECTDESC.md`。
- 权威 PRD、背景材料、旧架构图与开发计划进入稳定目录。
- 计划中的源码、prompt、模板、部署和测试目录以空占位文件纳入 Git。
- GitHub SSH 远端和基线提交。

### 4.2 基线验收

- 仓库除 `.gitkeep` 外不存在实现文件。
- README、PROJECTDESC 和本计划对 PRD 的关键边界表述一致。
- PRD 明确标为唯一权威规格；旧架构图明确标为待更新的历史材料。
- Git 工作树在基线提交后干净，远端 `main` 指向同一提交。

## 5. M0 · 地基

M0 不启用定时自动化，但会开始编写必要的 CLI、迁移、同步和冒烟测试代码。按以下顺序执行，避免在外部权限和本地路径未验证前建设业务链路。

### M0-1 · 工程与质量骨架

工作内容：

- 建立 Python 包元数据、依赖锁定、测试入口、静态检查和格式化规则。
- 建立最小 `wb` CLI，只包含帮助、版本与诊断入口。
- 定义配置分层：代码默认值、本机配置、环境变量覆盖、Keychain 凭据引用。
- 记录首次 ADR：运行时、CLI 框架、HTTP 客户端、schema 库和测试框架。

验收：全新环境可以安装开发依赖；帮助和诊断命令可运行；单元测试空骨架可执行；仓库无凭据。

### M0-2 · 工作目录与项目迁移

对应 PRD M0-1 至 M0-4：

- 在 Mac Studio 建立 `~/Documents/Work/`。
- 迁入 4 个指定项目，迁移前记录原路径、远端、分支和未提交状态。
- 修复 `HIC_Logistics` 文档中的过期绝对路径。
- 为缺失的 3 个项目建立 `AGENTS.md`，`CLAUDE.md` 只保留引用。
- 重配并验证 Claude Code 在新路径下的交互权限。

验收：4 个项目均可从新路径启动，Git 状态与迁移前一致，没有丢失未提交内容或远端配置。

### M0-3 · 工作 vault

对应 PRD M0-5 至 M0-7：

- 建立独立私有 `_vault` 仓库并继承 MyKnowledge conventions。
- 创建项目主笔记、全局 inbox、会议、审批、复盘、洞察和信号目录。
- 固化 frontmatter、固定区块和 inbox 机器可读格式。
- 整理 `HIC_Logistics/input/inbox.md`，使未处理数可稳定计算。

验收：4 个项目主笔记结构一致；全部样例 Markdown 通过 schema 检查；vault 私有 remote 可推送。

### M0-4 · 飞书身份与权限

对应 PRD M0-8、M0-10：

- 配置用户身份授权、最小权限和 refresh token 更新。
- 只申请日历只读、任务读写、视频会议/会议纪要只读及会议产物必要的文档只读。
- 用一场真实历史会议验证 `meeting_id → note_id → 完整文本`。
- 若 Note API 不可用，记录明确原因并验证本地文件导入路线可行。

验收：凭据仅存在 Keychain/运行环境；权限清单与 PRD 一致；冒烟测试结果可重复、可审计。

### M0-5 · 同步基础

对应 PRD M0-9：

- 实现 `work-sync`，遍历 `WORK_ROOT` 下选择加入的 Git 仓库。
- 对 dirty、冲突、无远端、网络失败给出明确状态，不做破坏性自动修复。
- 验证 `_vault` 与项目仓库均以 Git remote 为唯一真源。

验收：重复运行幂等；任何仓库失败不掩盖其他仓库结果；禁止 iCloud/Dropbox 同步含 `.git` 的目录。

### M0-6 · 云端模型冒烟测试

对应 PRD M0-11：

- 建立供应商无关模型适配边界和四类能力配置位。
- 首版用配置的会议模型处理一份真实长逐字稿。
- 验证长文本、严格结构化输出、token 记录、费用估算、超时和错误可见性。

验收：记录实际模型 ID、prompt 版本、输入输出 token 和估算费用；业务 schema 不含供应商专属字段。

### M0 退出门禁

PRD M0-1 至 M0-11 全部完成并留有验证记录后，才建立 M1 功能分支。飞书 Note API 冒烟失败不阻塞 M1，但必须启用并明确展示本地导入降级路线。

## 6. M1 · 会议进入第二大脑

M1 按可独立验证的纵向切片推进，每个切片都包含领域规则、适配器、持久化和测试，不先堆完所有底层再统一联调。

### M1-1 · 稳定 schema 与状态机

- 定义会议来源、逐字稿、结构化笔记、证据引用、审批候选、执行动作和处理状态。
- 定义 `discovered → fetched → archived → processed → pending-review → applied/ignored` 主状态及 `unavailable/failed` 分支。
- 定义 `meeting_id + note_id` 与本地内容哈希幂等键。

### M1-2 · 会议发现与原文归档

- 自动发现本人参加且可读取完整文本的全部已结束会议。
- 实现飞书 Note 主链路、本地投递与命令导入兜底。
- 原始录像只保留引用，不下载。
- 在模型调用之前先可靠保存完整逐字稿和来源元数据。

### M1-3 · 云端结构化处理

- 完整逐字稿优先单次发送；接近上下文上限时才临时分段并分层汇总。
- 严格区分事实、已形成决策、明确行动项、未决问题与 AI 建议。
- 每条执行性结果必须引用说话人和时间戳或稳定锚点。
- 初始调用失败后，同一模型指数退避最多重试 3 次；耗尽后保留原文、进入错误队列，不生成半成品。

### M1-4 · 集中审批与写回

- 生成 `_vault/review/meetings.md`，支持勾选批准、删除线加 `#ignore`、原地编辑。
- 批量应用前校验稳定 ID、目标项目、来源和最终写入位置。
- 路由规则：涉及他人或有期限进入飞书任务；明确内部下一步进入项目主笔记；未成熟想法进入项目 inbox；目标不明进入全局 inbox。
- 审批和拒绝均归档 AI 原值与用户最终值，重复应用不得产生重复写入。

### M1-5 · 状态、费用与提醒

- `wb status` 汇总发现、成功、不可用、失败、待确认、当月 token 和估算费用。
- 模型用量账本记录能力、模型、任务键、token、重试与调用时单价快照。
- 月度软预算只告警，不阻断新会议。
- 待确认达到 5 条或最老超过 3 天时通知；只在跨越阈值或升级时重复通知。

### M1-6 · 第二大脑问答

- `wb ask` 使用路径、frontmatter 和全文搜索筛选本地候选。
- 模型只能引用实际进入上下文的 Markdown；事实与建议分区；证据冲突并列展示。
- 默认不保存；`--save` 生成 `qa-insight`，且事实检索默认排除这类派生内容。

### M1-7 · 历史补导

- 仅按显式日期范围补导，开始前显示会议数、token 与费用预估。
- 逐场记录进度并支持中断续跑。
- 默认只沉淀知识；只有 `--include-actions` 才生成带 `historical` 标记的行动候选。
- 预计跨越软预算或高成本阈值时再次确认。

### M1 严格验收

逐项执行 PRD 第 6 章的 M1 严格验收（对应 L44）：3 场真实会议、批准/拒绝/修改、10 个真实问答、可恢复与耗尽故障、费用账本核对、积压边界测试。形成一份验收记录；全部通过前不开始 M2。

## 7. M2 · 晨间简报与周复盘

按以下顺序实现：

1. 飞书日历和任务事实采集；单源失败不阻断其余来源。
2. `WORK_ROOT` 项目扫描：Git、inbox、README 与主笔记下一步。
3. 信号快照与证据等级 E1/E2/E3。
4. 只输出条目 ID 排序和分组标签的模型排序器。
5. 模板渲染：事实区、提议区、最近完成、健康度和最多 5 个行动。
6. 每日 08:00 launchd、幂等重跑、写入、Git 推送与通知。
7. 每周一 07:30 周复盘、唤醒补跑以及简报有限等待。

验收：Mac Studio 连续 7 天自动生成简报并生成 1 份周报；事实区零错误、行动不超过 5 条、来源完整、重跑无重复。

## 8. M3 · 带上下文启动与收尾

- 从简报生成可点击的项目启动命令。
- 严格按 conventions、AGENTS、项目状态、近期会议、工作记录和任务指令拼接上下文。
- 会议完整逐字稿不进入默认上下文，只在核查来源时读取。
- 实现 Claude Code Stop hook：更新项目主笔记、追加工作记录并提交 vault。

验收：真实工作会话结束后自动写回；人工补充背景和补写记录的比例低于 20%。

## 9. M4 · 分流录入

- `wb task` 解析承诺和截止日期并创建飞书任务。
- `wb note` 在 5 秒内追加全局 inbox。
- 定期路由全局 inbox 到项目 inbox、项目主笔记、飞书任务或归档；任何执行性写回遵守审批规则。

验收：三类真实输入均进入正确落点，重复运行无重复，单次录入不要求打开其他 App。

## 10. 测试策略

| 层级 | 内容 | 是否允许真实外部调用 |
|---|---|---|
| 单元测试 | 领域状态机、路由、幂等键、预算、证据等级、Markdown 解析 | 否 |
| 契约测试 | 飞书响应、模型结构化输出、配置与 schema 兼容性 | 否，使用去敏 fixture |
| 集成测试 | 临时 vault、Git 仓库、错误队列、用量账本、CLI 退出码 | 默认否 |
| 验收测试 | 真实飞书租户、真实会议、云端模型、launchd 与 macOS 通知 | 是，但必须显式运行 |

所有修复先补失败测试。外部 API 失败、重复触发、部分写回失败、token 过期和主机唤醒补跑都必须有专门场景。任何日志或测试产物不得包含凭据或未经去敏的真实会议内容。

## 11. 提交与发布门禁

每个工作包合并前必须：

- 对应测试通过，且没有静默忽略的失败。
- 文档、prompt、schema 和实现保持同一版本语义。
- `git status` 不包含运行产物、凭据、真实转写或本机绝对路径。
- 对外写操作有 dry-run 或明确确认边界，并通过幂等测试。
- 新增外部权限、数据外传范围或供应商耦合时先写 ADR，并确认没有违反 PRD。

里程碑完成时生成验收记录并打基线标签；验收失败只修当前里程碑，不提前开发下一里程碑。

## 12. 下一开发批次

下一次开始写代码时，只执行 **M0-1 工程与质量骨架**：

1. 检查 Mac Studio 的 Python、Git、Keychain 与 launchd 环境。
2. 选定并记录运行时、CLI、HTTP、schema 和测试工具 ADR。
3. 建立最小包元数据、依赖锁定与 `wb` 帮助/诊断入口。
4. 建立第一批配置加载、路径解析和秘密值保护测试。
5. 运行全套基础检查并提交 M0-1；通过后才进入工作目录迁移。

本批次不实现飞书、模型、会议、简报或写回功能，目的是先得到一个可安装、可测试、可安全扩展的工程底座。
